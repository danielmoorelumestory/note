## Context

`syncAll` 读取云端全部记录，与本机记录、本机删除标记合并（同一 id 取更新时间较新者），再 `PUT` 整份结果；`pushRecord` 读取整表、替换一条、`PUT` 整表。Worker 的 `PUT` 在一个批处理里先 `DELETE` 该密钥下全部行，再逐条 `INSERT`。每条记录带 `updatedAt`（缺省时用 `savedAt`），墓碑记录是 `{ id, savedAt, updatedAt, deleted: true }`，客户端保留 180 天后不再上传。

问题：读取与写回之间若另一台设备写入了新版本，这个窗口里的修改会被整表覆盖掉；整表写回的数据量也比必要的大。

localStorage 中回测记录（`grid-trading-saved-v1`）与日K 缓存（`grid-trading-candles-v2:*`）、四年高低缓存（`grid-trading-extremes-v1:*`）共用同一份额度；缓存可随时重新生成，记录不可。`writeRecords` 直接调用 `setItem`，额度满时会抛出异常。

## Goals / Non-Goals

**Goals:**
- 同步写入不会用较旧的版本覆盖云端较新的版本。
- 不改客户端协议，新旧版本互相兼容，部署顺序无风险。
- 存储额度不足时，回测记录优先保存，缓存让位。

**Non-Goals:**
- 不迁移到 IndexedDB。
- 不做客户端只上传变更记录、不做冲突合并 UI。
- 不改记录的数据结构。

## Decisions

**1. 服务端写入按记录 upsert，带时间守卫。**
`INSERT ... ON CONFLICT(owner_hash, record_id) DO UPDATE ... WHERE <新版本时间> >= <现有版本时间>`，时间取 `COALESCE(payload.updatedAt, payload.savedAt, '')`（均为 ISO 字符串，字典序即时间序）。相等时也覆盖，使重复上传保持幂等，并允许 `refreshRecord` 这类不改 `updatedAt` 的行情刷新结果写入。
备选：给每个密钥加整体版本号、用乐观锁拒绝过期的整表写入。放弃原因：会让整表写回频繁失败并需要客户端重试逻辑，改动更大。

**2. 守卫的语义在 SQL 里，不在代码里。**
每条记录一条语句，放进同一个 `batch`，保证原子。被守卫挡住的记录通过 `meta.changes === 0` 识别，响应返回 `skipped: [id...]`。客户端目前不读这个字段，旧客户端不受影响。
备选：先 SELECT 再决定。放弃原因：两次往返且仍有竞态。

**3. 不再整表删除，墓碑到期后在写入时清理。**
删除由墓碑 upsert 表达，所以不需要整表删除。墓碑的 `updatedAt` 超过 180 天（与客户端 `TOMBSTONE_TTL` 一致）时，在每次 `PUT` 末尾删除这些行，防止永久堆积。
风险点：客户端已不再上传过期墓碑，所以服务端留下的过期墓碑不会再被覆盖，只能由这个清理逻辑删除。

**4. 客户端协议不变。**
`syncAll`、`pushRecord` 都不改。旧页面（浏览器缓存的旧版本）对新 Worker 仍然正常：它们上传的整份结果经过守卫后只会更新较新的记录。
备选：`pushRecord` 只上传单条。放弃原因：如果新客户端遇到尚未部署新语义的旧 Worker，旧 Worker 会因整表删除而丢掉其余记录，产生部署顺序依赖；保持协议不变则没有这个风险。

**5. 浏览器存储：缓存让位于记录。**
新增 `evictCaches()`，删除所有以日K 缓存、四年高低缓存前缀开头的 localStorage 键，以及报价缓存（sessionStorage）。`writeRecords` 在 `setItem` 失败时调用它并重试一次；缓存自身的 `writeJson` 失败时也先清理其他标的的缓存再重试一次，仍失败则放弃（缓存只是优化，不影响正确性）。
备选：按最近使用顺序只清一部分。放弃原因：缓存重新获取成本低（云端日K），全清最简单且不会再次写失败。

**6. 市场数据的 upsert 加“值有变化才更新”条件，降低 D1 写入量。**
D1 免费版每天最多写入 10 万行，且 `ON CONFLICT DO UPDATE` 即使新旧值完全相同也算一次行写入。分钟线每次抓取都带 640 根的重叠窗口，原先每次重写 7,680 行（12 个标的），一天三次定时抓取再加调试时的手动补抓就会耗尽额度；额度用尽后所有写入（包括用户记录同步）都会失败，直到 UTC 零点。给三处 upsert 加 `WHERE 旧值 IS NOT 新值`（对 `NULL` 也安全），重复抓取同样的数据写入行数为 0。预计常态写入降到每天约 3 千行（只有新增分钟 + 最后一根可能变化的分钟 + 少量日K/偏移）。
备选：减少抓取次数或窗口。放弃原因：抓取次数是为防断档设计的，窗口由接口决定；去掉无效写入才是根本办法。

## Risks / Trade-offs

- [时间字符串格式不一致导致守卫误判] → 客户端统一用 `toISOString()` 生成；记录缺失两个字段时按空字符串处理（视为最旧）。
- [墓碑清理误删仍需要的墓碑] → 只删 `deleted` 为真且 `updatedAt` 早于 180 天的行，与客户端上传规则一致。
- [D1 写入额度用尽后同步全部失败] → 本变更降低常态写入量；写入失败时 `PUT` 返回带原因的 500 JSON（此前是不带原因的 1101），便于定位。额度在 UTC 零点恢复，期间读取不受影响，本机修改仍保存在浏览器里。
- [同一时刻两台设备写同一条记录] → 以较新的 `updatedAt` 为准，较旧者被忽略，这是预期行为，不再是“后到者覆盖”。
- [缓存被清空后首次加载变慢] → 日K 来自云端，影响很小，且仅在额度已满时才发生。

## Migration Plan

1. 部署前导出云端 D1 备份（`wrangler d1 export`）。
2. 部署 Worker（无新表）。
3. 用一个临时的测试密钥验证写入语义，验证后清理测试数据，不触碰真实记录。
4. 推送前端改动。回滚：重新部署上一版 Worker 与前端即可，数据结构未变。
