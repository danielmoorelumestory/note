## Context

分钟线由 `workers/grid-trading-sync` 的 Cloudflare Worker 抓取并存入 D1（`minute_bars`），前复权偏移存于 `daily_offsets`。腾讯 `mkline` 接口一次最多返回最近 640 根 1 分钟线（约 2.7 个交易日），无法回溯更早的数据，所以 1 分钟线一旦断档就无法补回。目前定时任务每个交易日只在 15:10（UTC 07:10）跑一次，写入使用 `INSERT OR IGNORE`，没有任何运行记录，也没有办法发现已发生的缺口。

`daily_offsets` 每次抓取都会按最新除权信息重写，覆盖从最早分钟线日期起的所有交易日，因此天然包含每个标的的交易日列表，可作为“应有哪些交易日”的基准。

## Goals / Non-Goals

**Goals:**
- 降低断档概率：同一交易日多次抓取，单次失败有重试机会。
- 发生问题时可追溯：每次抓取留下日志。
- 已经发生的缺口能被发现，并在详情页提示。
- 提供手动补抓入口，必要时不必等定时任务。

**Non-Goals:**
- 不回填历史分钟线（接口不支持）。
- 不存 5 分钟及以上周期。
- 不做主动通知（邮件/推送），本次只做页面提示和日志。
- 不改变分钟线读取接口 `/minute` 的返回格式。

## Decisions

**1. 多次触发，靠重叠窗口去重。**
cron 增加到每个工作日 15:10、16:00（北京时间）和次日 09:00 三次：`10 7 * * 1-5`、`0 8 * * 1-5`、`0 1 * * 1-5`（UTC）。每次都抓最近 640 根，窗口天然重叠，按 `(code, ts)` 主键处理，多跑没有副作用。
备选：在一次运行里失败后立即重试。放弃原因：接口故障往往持续一段时间，立刻重试大概率仍失败；拉开时间间隔的重试更有效。

**2. 写入改为 `INSERT ... ON CONFLICT(code, ts) DO UPDATE`。**
让后抓到的数据覆盖先前的值。盘中抓到的最后一根 K 线可能还没走完，用 `OR IGNORE` 会让不完整值永久保留。覆盖不会增加行数，只是多一次更新写入。
备选：保持 `OR IGNORE`，仅在收盘后运行。放弃原因：无法保证每次运行都在收盘后（手动补抓、时区错误），覆盖式更稳妥。

**3. 新增 `sync_log` 表。**
字段：`id`（自增）、`run_at`（毫秒时间戳）、`trigger`（`cron` 或 `manual`）、`code`、`ok`（0/1）、`fetched`（本次抓到根数）、`first_ts`、`last_ts`、`error`。每次运行每个标的写一行。日志只增不删；按每天约 3 次 × 标的数估算，一年约 1 万行，体量可忽略，暂不做清理。
备选：只记录失败。放弃原因：成功记录用于“最近一次成功抓取时间”，没有它就无法区分“没跑”和“没问题”。

**4. 完整性检查以 `daily_offsets` 为交易日基准。**
对每个标的，取 `daily_offsets` 中从最早分钟线日期起的所有交易日，与 `minute_bars` 中每天的根数比较；某个交易日根数少于 241 即为缺口，同时记录缺失根数。交易日当天且当前时间早于 15:10 的，不判为缺口（尚未收盘）。
备选：自建交易日历。放弃原因：节假日规则维护成本高，而日K 数据已经天然给出了交易日。
已知限制：个别标的某天停牌，分钟线本来就不足 241 根，会被误报为缺口；通过“当天日K 成交量为 0 则跳过”处理会增加复杂度，本次先不处理，在提示文案里写明“可能为停牌”。

**5. 状态接口只读，复用现有认证。**
`GET /minute/status?code=` 沿用现有的 `Authorization: Bearer` 密钥检查，返回：
`{ code, lastSuccessAt, lastFailure: { at, error } | null, gaps: [{ date, bars, missing }] }`。
`gaps` 只包含最近 30 天，与详情页读取分钟线的范围一致，避免历史上一次性缺口永久占据提示位置。

**6. 手动补抓：`POST /minute/sync`。**
带同步密钥即可触发一次与定时任务相同的流程，`trigger` 记为 `manual`。为避免滥用，限制为只抓取该密钥下已保存记录里的标的，并受已有认证保护。
备选：把手动补抓做成页面按钮。放弃原因：先用命令行即可，按钮属于后续可选项。

**7. 页面提示放在详情页分钟线区块。**
读取状态失败不影响分钟线本身的展示。提示仅在以下情况出现：存在缺口；或最近一次成功抓取距今超过 4 天（说明断档即将发生或已发生）。文案举例：“2026-10-12 缺失 120 根分钟线（可能为停牌）”。

## Risks / Trade-offs

- [腾讯接口整体不可用或改版] → 日志能暴露问题；但无法自动恢复，需要人工处理。窗口只有 2.7 个交易日，需要在这段时间内发现并修复。
- [停牌日被误报为缺口] → 文案标注“可能为停牌”，不影响数据本身。
- [覆盖写入增加 D1 写入次数] → 每天 3 次 × 标的数 × 640 行，12 个标的约 2.3 万行写入/天，远低于 D1 免费额度（10 万行/天）；标的增多到约 40 个时需要重新评估。
- [多次 cron 触发在同一分钟并发写入] → 三个触发时间间隔足够，且主键冲突走覆盖，不会产生重复行。
- [cron 表达式和 Worker 部署需要用户手动执行 wrangler] → 在任务里写明部署与建表命令。

## Migration Plan

1. 在 `schema.sql` 新增 `sync_log` 表，执行 `wrangler d1 execute grid-trading-sync --remote --file=schema.sql`（`CREATE TABLE IF NOT EXISTS`，可重复执行）。
2. 修改 Worker 代码与 `wrangler.jsonc` 的 cron，`wrangler deploy`。
3. 部署后用手动补抓触发一次，确认 `sync_log` 有记录、`/minute/status` 返回正常。
4. 回滚：重新部署上一版 Worker 即可；`sync_log` 表保留不影响旧代码。
